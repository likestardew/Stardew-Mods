## 0. 要解决的问题

现补丁（限速+门控+认领，v4b_realfilter）在审计修正后的模拟里清场持平到更快、CPU 更省、防扎堆有效，
但**真实游戏实测**（用户 2026-09-28 实测：左地块 1 小屋 6 只/576 株 原版 10/11.5h vs 补丁 10.5/10.5h；
右地块 2 小屋 12 只/1152 株 原版 11/11h vs 补丁 12/11h；清场期尖峰补丁更多、越到后面效率越低）
与模拟存在缺口，且饱和清场期 A* 是原版 2~3 倍。根因：v4b 仍是**反应式**调度——每次决策都做一次
"最近可动作格" A*（limit 100），决策频率事件驱动但扎堆时失败/影子重搜翻倍。

用户的新思路：**把"找活"从每次决策搬到周期性全量扫描 + 一次性分配**，之后祝尼魔按分配路线执行，
扫描之间零搜索。本设计把该思路补全为可实现、可量化的算法，并在修正模拟器里回答核心问题：
**扫描+分配的成本是否真的有界（不重蹈 v2b 密集田扫描爆炸的覆辙）**。

## 2. 扫描模型

### 2.1 全量扫描（assign 模式的唯一"感知"来源）

- **频率**：两档，5s = **300t**（assign5）、10s = **600t**（assign10）（60t = 1 游戏秒）。
- **错峰**：`hut i 的扫描相位 = i × period / 小屋数`。双小屋：A 在 `t ≡ 0 (mod period)`、
  B 在 `t ≡ period/2 (mod period)`——两个小屋的扫描+分配突发永不重叠。
- **成本计量**：一次全量扫描 = 读 (2r+1)² = **841 tile**（r=14；模拟里按小屋自己的盒
  `[hx+1−r, hx+r]×[hy+1−r, hy+r]` = 28×28=784 格）+ 每格一次"是否有成熟作物"检查。每格记 1 次
  **tile inspection**（单独指标，与 A* pops 分开记）。
- **等效换算**（保守上下界）：一次 A* 出队扩展 ≈ 堆出队 + 4 邻居的 passable/closed/gScore 查表 + 入堆，
  ≈ 1~3μs；一次 tile inspection ≈ terrainFeatures/objects 字典查表 + readyForHarvest 检查 ≈ 0.1~0.3μs。
  取 **1 A* pop ≈ 10~30 次 tile inspection**：10× 是对"扫描贵"最保守的折算（下界），30× 是宽裕上界。
  → 一次全量扫描 ≈ **784 insp ≈ 26~78 pop 当量 ≈ 0.3~0.8 个 limit-100 A\* 搜索**。
  每 300t 一次 = 平均 **2.6 insp/tick/小屋 ≈ 0.09~0.26 pop 当量/tick**——对比原版稳态 ~1-3 pops/tick，
  低一个数量级以上。**有界性不依赖作物密度**（读的格数恒为盒大小，与株数无关）。

### 2.2 增量比对（"不用每次全量重排"的实现）

扫描读格子是廉价的；贵的是**重排**。所以增量做在重排层：

- 每只祝尼魔记录**预期状态** = 当前路线（Route，≤ ROUTE_LEN 个待收格，全局登记表
  `routeTargets: tile → junimo`，收获事件即时注销）。
- 下次扫描（小屋自己的盒）先 diff：
  1. **路线核验**：该小屋每只有路线的祝尼魔，其路线格是否全部仍在 ripe 集合里（本小屋路线格必然
     在本小屋盒内，全量扫描顺带完成核验，零额外读格）。全在 → **健康，不重规划**（走路的继续走，
     站等的等路线推进）。
  2. **分歧者**：路线任一格消失（单小屋场景只会来自重叠区外小屋收割；双小屋场景即跨小屋冲突）→
     该祝尼魔进入重排集合 R，其剩余路线格释放回池。
  3. **分歧率** = |分歧者| / max(1, 有路线的祝尼魔数)。**分歧率 ≤ X 且无新波次** → 只重排 R
     （增量模式）；**分歧率 > X 或发现新熟作物**（ripe − (routeTargets ∪ pool) 非空，即波次/日初）
     → **全量重排**（R = 本小屋全部非收获中祝尼魔）。X 默认 **0.5**，扫参 {0.25, 0.5, 1.0}。
- **"也许不用全量扫描？"的回答**：全量**读格**必须保留——祝尼魔收割事件只注销自己的路线格，
  新熟作物（波次/次日新熟）没有任何事件钩子，只能靠读格发现；而 841 insp/300t 的成本已被 2.1 证明
  与一次 A* 同量级。真正省不掉读格的方案（只核验路线格）会把波次发现延迟到任意久，故不采用；
  作为对照扫参点实现了 **hybrid 模式**（每第 3 次扫描全量、其余只读路线格 Σ≤ROUTE_LEN×8 格，
  代价是波次发现延迟最多 3×period），在双小屋 d=1.00 格实测其取舍（§6）。
- **增量重排的成本**：健康祝尼魔在扫描时只花 O(路线长) 的集合查询；只有分歧者/闲逛者进入分配计算。

## 3. 分配算法

### 3.1 问题

6~8 只祝尼魔 × ~784 格盒内 ≤ ~740 株成熟作物，最小化**总清场时间**（= makespan：各祝尼魔
行走+采摘时间线的最大值）。精确最优 = 带路线的多旅行商，不可行。选择**有界启发式**：

**每扫描点的"一目标+短路线"分配**（滚动执行，扫描间隔 5s/10s，远短于清场总时长 → 滚动近似）：

1. **候选集截断（防爆炸的关键）**：每只待分配祝尼魔只考虑离它**曼哈顿距离最近的 m=32 株**（r=14 盒内
   对角线 ~40 格，32 株覆盖半径 ~8-10 格——分配最优解几乎不会舍近求远超出此范围）。
2. **遗憾值贪心（regret greedy，近似匈牙利）**：对每只 j ∈ R 取其候选中 cost 最小/次小，反复选
   "次小−最小"最大者固定分配（目标从池中移除），直到 R 空 or 池空。O(|R|²·m) ≤ 8²×32 = **2048 次比较**。
3. **路线延伸**：每只已分配者从其目标出发，在剩余池中做最近邻延伸至 ROUTE_LEN 个目标
   （最近邻 O(k·|R|·|pool|) ≤ 5×8×784 ≈ **31k 次距离计算**）。路线 = 区内最近邻 TSP 路径。
4. **直接寻路**：每只新分配者对路线第一目标做**一次** A*（limit 300，曼哈顿启发；失败 → 该株标记
   本扫描不可达，祝尼魔闲至下轮扫描）。之后路线推进各做一次 A*（到达收获完成后）。
   ——这就是与原版的本质区别：**没有"到达后找最近"的开放式搜索，每次寻路都有唯一确定终点**。

**复杂度上界**（每小屋每扫描点）：`O(841 读格 + |R|·m + |R|²·m + k·|R|·|pool| + |R| 次 A*)`
≈ 784 insp + **~35k 次基本运算** + ≤8 次 A*（≤300 pops，实际 ~60-150）。
35k 基本运算 ≈ 120~350 pop 当量（1 pop ≈ 100-300 基本运算）。**合计 ≈ 每 300t 每 小屋
~1-2 个 limit-100 A\* 的当量**，与株数无关（|pool| 项线性但常数极小），复杂度 ≪ 扫描间隔
（300t = 5s 真实时间，该计算 <0.1ms）。**v2b 的死因（决策时刻全表扫描 + 1000 预算 A* + 2t 重试风暴）
在这里结构上不可能发生**：分配只发生在扫描点、候选集有截断、闲逛者直接睡到下轮扫描（无重试环）。

### 3.2 路线长度与扫描间隔配比

路线必须撑满扫描间隔，否则祝尼魔在两次扫描之间断粮（空转）。设单位作物周期 ≈ 61t（WF）+
平均行走 ~40t：ROUTE_LEN ≈ ⌈period/100⌉。**assign5 → ROUTE_LEN=3；assign10 → ROUTE_LEN=5**。
扫参 ROUTE_LEN ∈ {2,3,5}（5s 档，单小屋 d=1.00 jn=6）验证配比敏感性。

### 3.3 与原版目标选择的对比

- 原版/v4b：每次决策一次"最近可动作格"开放搜索（出队序近似由近及远），扎堆时多只同目标 →
  陪站 120t（doomed）或到达落空（wasted）；v4b 用认领过滤缓解，代价是失败后的无过滤影子重搜。
- assign：分配即互斥（一株至多进一条路线），**同小屋内部冲突结构性为零**；双小屋重叠区由
  **全局路线登记表**互斥（B 小屋扫描时避开 A 小屋在册路线格，登记表由收获事件即时维护，
  陈旧度 ≤ 对方扫描间隔）→ 跨小屋冲突也结构性趋零。代价：重叠区作物可能被"留给"对方直到
  对方路线清完（轻微的等待，不是冲突）。

## 4. 与游戏决策钩子的对接（事件驱动，绝每帧轮询）

mod 实现映射（真实代码落点）：

| 游戏事件 | 原版/v4b 行为 | assign 行为 |
|---|---|---|
| `PatchPathfindDoWork`（pathfindToNewCrop，70% 门/430t poke/收获完成触发） | 开放最近搜索 + 失败链 | **替换为路线推进**：有路线 → 走向 route[0]；无路线 → 睡到本小屋下次扫描。**poke 对 assign 是 no-op**（不重排、不搜索） |
| 到达 `tryToHarvestHere` | 收获或"无事"poke | route[0] 在 → 原版收获流程（2000ms/WF 61t，1000ms crossing 收走）；不在（被外小屋收走）→ **改道**：取 route[1] 再做一次 A*；路线空 → 自补（见下）或睡到下轮扫描 |
| 收获完成（2000ms 计时归零） | pokeToHarvest（70% 门/WRF 补刀） | **路线推进**：pop route[0]，route[0] 仍熟（1 次读格核验）→ A* 到 route[1]；路线空 → **自补**：直接查分配表取最近 1 株（0 读格，环形最近邻 + 一次 A*），表空才睡到下轮扫描（§8 修订 1） |
| 生成 `JunimoSpawnHelper`（60t 节流 + 扫描有活） | 60t 缓存盒扫描（841 读格/60t） | **登记表查询**（池∩盒∩可达非空，0 读格）；出生即从池做单祝尼魔最近邻分配（O(|pool|)，出生是稀有事件） |
| 430t 双发 poke | 两轮 70% 判定，walker 被打断重寻 | no-op（路线在身，不需要重决策；这是分配制削峰的来源之一） |

事件集 = {到达, 收获计时归零(路线推进), 扫描点, 生成, (v4b/legacy 才有)双发 poke}。
**没有任何逐帧轮询**；闲逛的 assign 祝尼魔 NextEventTick = 下次本小屋扫描 tick，事件堆零负担。

## 5. 与现有门控/限速/认领的关系（结论）

- **决策限速（20t/40t cap）：assign 不需要。** assign 的搜索只有两类且都有硬上界：扫描点分配 A*
  （≤|R| 次/扫描点）+ 路线推进 A*（每次收获至多 1 次，被采摘周期天然节流 ≈0.6 次/s/只）。
  扫描周期本身就是限速器。cap_only/v4b 照常带 cap（那是被测补丁的一部分）。
- **扫描门控（60t 缓存）：assign 不需要。** 感知已整体替换为周期扫描；生成检查用登记表。
- **认领过滤：assign 不需要。** 互斥由分配表结构性保证（含跨小屋）。CropClaims 表在 assign 模式下
  退役（保留 v4b 组的建模用于对照）。
- 换句话说 assign = "感知换周期扫描 + 决策换路线执行"，v4b 的三件补丁铠甲全部退役。

## 6. 边界情况

| 情况 | 处理 |
|---|---|
| 祝尼魔重生/消失 | assign 祝尼魔无 25% 回家掷骰（无失败链 → 不 despawn）；防御式处理：扫描时若见 WaitingRespawn 者仍持有路线 → 释放回池；重生者出生即重新分配 |
| 不可达作物 | 地图生成按 BFS 可达过滤（单小屋）；双小屋下**按小屋**的可达集过滤分配池（A 不可达的株不进 A 的池）；残余不可达（预算内 A* 失败）→ 该株本扫描拉黑、祝尼魔睡到下轮，不重试风暴 |
| 作物波次新熟 | 无事件钩子，由下次扫描发现（延迟 ≤ period）；发现即触发全量重排。hybrid 扫描模式下延迟至多 3×period（扫参实测代价） |
| 换天 | dayUpdate：清空路线登记表/池/扫描相位（等价 CropClaims.Clear） |
| farmhand | 分配只由主游戏（IsMasterGame）计算（与 CropClaims 同前提）；farmhand 客户端只看动画，不建模 |
| 双小屋重叠 | 全局路线登记表互斥 + 各自错峰扫描；重叠冲突指标单独统计（wasted/doomed 按跨小屋拆分） |
| 限速/门控 | 见 §5：退役；对照组保留完整 v4b 行为 |
| 小屋被围死 | 聚合层剔除（reachable 候选=0 的图）并计数（沿用 B9 防护，双小屋按"任一小屋"判定） |

## 8. 实现后的设计修订（以实现为准，均为量化验证后所做）

实现与扫参过程中发现并修正了三处设计缺陷，最终形态以本节为准：

1. **路线耗尽即时自补（SelfAssign）——消除周期量化损失（关键修订）。**
   初版严格按 §3"路线耗尽 → 睡到下次扫描"实现，扫参出现剧烈锯齿（route=3 与 6 好、4 与 5 差
   15~40%）：路线周期与扫描周期**对齐**时祝尼魔恰好在扫描点上空闲（集体重分配），错开时平均空转
   半个周期。诊断显示 route=4 时 wait=15%、walk=46%。修订：路线耗尽（收获完成事件）时**直接查
   分配表**（`pool ∩ 本小屋盒 ∩ 可达`，零读格）取最近 1 株自补，路径失败或池空才睡到下次扫描。
   成本每次至多一次环形最近邻查询（~30-400 次基本运算）+ 一次 A*，每收获至多触发一次——仍然远
   低于 v2b 的"每次决策全盒扫描+1000 预算 A*"。效果：wait 15%→0-1%，route 长度完全不再影响
   吞吐，扫描退化为纯感知 + 空闲者集体分配（波次到达/终局）。出生同样改为出生即自补（消除启动
   延迟）。分配的互斥性与"感知只发生在扫描点"的性质不变。
2. **直达寻路预算 300 → 10000。** 初版用 300 预算导致**末期 livelock/DNF**：剩余远端作物（40+
   格路径）的 g+h 菱形需数千次扩展，每次扫描全部失败。游戏本体对同类长路径（`returnToJunimoHut`）
   用的就是 limit 10000，分配制直达寻路采用同值。代价（末期远距 A* 的菱形成本）如实计入 pops。
3. **混合扫描首扫必为全量。** hyb 模式初版首次扫描被判为 partial，池在 t=1 未被填充，出生推迟
   ~500t。修正为首次扫描恒为全量。

扫参结论（详见 REPORT.md §扫参）：修订后 ROUTE_LEN 与分歧阈值 X 对结果**不敏感**（自补机制使
扫描时集体分配仅覆盖空睡者），两参数保留为保险；混合扫描（每第 3 次全量，其余只核验路线格）
读格省 3.0×，在基准波次密度下清场与日吞吐零损失，代价是波次发现延迟 298→793t（上界 3×周期）。
主网格取保守的全量扫描。
